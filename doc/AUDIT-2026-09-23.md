# March 4 / March 5 Viability Audit

Date: 2026-09-23

This audit describes the current working trees, not just the last committed
revisions. March 4 was clean at the start of the audit. March 5 already had
uncommitted changes in its catalog/surface/interaction-net work and in the
Hello World database; those changes were preserved.

## Executive conclusion

March 4 and March 5 are both useful, but at different layers.

- **March 4 is a real CID-backed VM implementation**, not a conventional VM
  with no content addressing. It content-addresses compiled words,
  quotations, literals, strings, and type signatures in SQLite, then links CID
  references to runtime cells/native primitive addresses.
- **March 4 is not currently a dependable primary implementation.** Its VM
  kernel builds and passes its small direct suite, but its compiler test suite
  has drifted out of buildability, its language-level files are not a true
  automated test suite, and important memory-management analysis is disabled.
- **March 5 is the strongest place to resume implementation.** It has a safer
  Rust codebase, a compact content-addressed object model, a working graph
  builder/interpreter, and 63 passing tests in the present working tree.
- **March 5 does not yet validate the interaction-net approach.** The code that
  executes words is a recursive evaluator for a CID-addressed dataflow DAG.
  The actual active-pair interaction-net reducer is separate scaffolding with
  only early rules, and there is no graph-to-net lowering or interpreter
  fallback path yet.
- **Neither implementation is ready to be declared authoritative without a
  short stabilization phase.** March 5 has a critical primitive-identity bug;
  March 4 has an analogous weaker-CID problem and substantial test drift.

Recommended direction: use March 5 as the integration trunk for the canonical
object model, front end, reference interpreter, and tests. Preserve March 4 as
the VM/backend laboratory and source of language semantics. Define a small
backend-neutral semantic IR contract before committing the language to either
the VM or interaction-net representation.

## CID findings

### March 4 really is CID based

The path is implemented, not merely documented:

1. The compiler emits a variable-length blob containing two-byte primitive
   tags and 32-byte CID references.
2. `db_store_blob` hashes the blob and persists it in SQLite.
3. Word dictionary entries carry the compiled blob CID.
4. The loader recursively resolves word, quotation, and data CIDs, caches the
   results, constructs runtime cell streams, and supplies native primitive
   addresses.
5. The runner lazily specializes token-stored definitions, persists the
   result, links its CID, and executes it in the VM.

March 4 therefore already contains much of the content-addressed execution
idea later made more explicit in March 5.

### March 4 CID weakness

`db_store_blob` hashes only `data`, while `kind` and `sig_cid` live beside the
hash. Consequently, identical bytes with different semantic kinds or types
collide. `INSERT OR IGNORE` retains whichever metadata was stored first. A CID
does not fully identify a typed object.

Primitive IDs are stable numeric capabilities rather than hashes of primitive
semantics or ABI. That can be a valid ABI design, but those identifiers should
not be described as content identities unless the stable ABI/version is itself
part of the identified object.

### March 5 critical primitive-identity defect

The canonical primitive object contains only:

```
[object_tag, zero_root, params, results, effects, effect_mask]
```

It contains no operation identity or implementation/ABI identifier. Therefore
all primitives with the same signature and effects have the same CID.

This was reproduced with the CLI:

```
add_i64 -> 8a4a62071a5b220eefd5a702cceca026ca5abc4e3590878a12bb314022702682
sub_i64 -> 8a4a62071a5b220eefd5a702cceca026ca5abc4e3590878a12bb314022702682
```

Only one `prim` object is stored. Both names point to it. The interpreter then
looks up mutable names for the CID to decide what operation to perform and uses
a hard-coded priority list when several names exist. In a store containing both
names, `add_i64` wins over `sub_i64`.

This violates the central CID invariant: the behavior of a referenced object
is not determined by its content. It must be fixed before new language work.

A primitive object needs an identity-bearing field such as a stable opcode plus
ABI/version, or an implementation CID. Human aliases can remain outside the
object, but semantic operation identity cannot.

## March 4 viability

### Assets worth retaining

- A working direct-threaded VM kernel and compact linked representation.
- A functioning compiler/loader path for several representative programs.
- Static stack typing and overload machinery.
- Lazy call-site specialization and specialization caching.
- A sizable language corpus covering quotations, loops, arrays, mutation,
  maps, strings, and memory-management experiments.
- The most complete expression of the intended heap-graph/liveness design.

### Blocking problems

1. **Tests no longer guard the compiler.** Public API and linker changes were
   not propagated to tests or Makefile link lines.
2. **The language corpus is not a harness.** Many files are demonstrations or
   historical probes without assertions; deferred compilation makes
   compile-only success misleading.
3. **The memory-management claim is ahead of reality.** The rebuilt compiler
   warns that `emit_free_for_dead_nodes`, `free_slot`, and `type_is_heap` are
   unused, and runtime traces explicitly report that dead-node FREE emission is
   disabled for testing.
4. **Syntax history is mixed together.** Parentheses are both historical
   comments in tests and current quotation syntax.
5. **There are native crashes.** Some map executions still segfault, so a bad
   language program can take down the compiler/runner process.
6. **The code mixes generations.** Legacy cells, CID blobs, token definitions,
   immediate compilation, and ref-graph work coexist, making local fixes prone
   to crossing obsolete paths.

### Verdict

March 4 is viable as a backend prototype and semantics/reference corpus. It is
repairable, but making it the primary trunk would first require rebuilding its
test boundary and deciding which compiler generation is authoritative.

## March 5 viability

### Assets worth retaining

- Clear separation between immutable objects and mutable name indexes.
- Canonical encoders for nodes, words, interfaces, namespaces, effects, guards,
  and state snapshots.
- A useful Forth-like `GraphBuilder` that lowers stack operations to explicit
  edges.
- Explicit RETURN nodes supporting zero, one, and multiple results.
- Structural effect dependencies and multi-domain token threading.
- A reference interpreter with argument/result checks.
- Guard, dispatch, deopt, quotation, and state prototypes with passing tests.
- Rust makes malformed data and evolution substantially easier to contain than
  the March 4 native runner.

### Blocking problems

1. **Primitive semantic identity is missing from the CID** (priority zero).
2. **Persistent-format evolution is unmanaged.** The repository's own example
   database cannot be decoded. There is no format version, migration tool, or
   policy for old immutable objects.
3. **The current graph is not an interaction net.** `NodeCanon` is a typed
   content-addressed dataflow DAG. The actual `inet::Net` is a different model
   with principal ports and active-pair rewriting.
4. **The interaction-net execution path is incomplete.** There is no
   graph-to-net translator, no core rule set for calls/control/effects, and no
   hybrid reducer/interpreter path. The planning document explicitly lists
   these as next steps.
5. **Native compilation is a proof of mechanism, not a backend.** `exec.rs`
   contains fixed machine-code stubs only for add and subtract; `code_cache` is
   schema/documentation only.
6. **Primitive execution depends on mutable names.** Even after repairing the
   collision, the interpreter should dispatch through immutable semantic
   identity or a verified runtime binding table, never whichever aliases happen
   to exist in `name_index`.
7. **Types are still a small concrete enum.** March 4's polymorphic stack/type
   work has not yet been carried forward.

### Verdict

March 5 is the better primary implementation base, provided the object model is
stabilized before feature work. It currently demonstrates a promising
CID-addressed graph interpreter, not a viable interaction-net backend.

## Recommended architecture

Keep three distinct layers:

```
surface syntax and compile-time words
                |
                v
backend-neutral typed semantic graph/IR
       |                       |
       v                       v
reference DAG interpreter   optional lowerings
                            /              \
                         VM backend      INet experiment
```

The canonical semantic graph should state observable language meaning:

- ordered inputs and outputs;
- types/type variables and specialization keys;
- calls, quotations, branches, and returns;
- explicit effect/capability dependencies;
- allocation, ownership/aliasing, and lifetime obligations;
- stable primitive semantic IDs and ABI versions.

It should not embed x86 addresses or require interaction-net reduction for its
meaning. A VM lowering and an interaction-net lowering can then be tested
against the same reference interpreter and conformance vectors.

This direction aligns with the root semantic specification, which already
describes VM and interaction nets as lowerings of a backend-independent IR.

## Recovery sequence

### Phase 0: preserve and establish the baseline

1. Keep all current nested repositories and uncommitted March 5 work intact.
2. Decide repository ownership: retain nested repositories intentionally or
   make the outer repository documentation-only. Do not casually flatten Git
   histories.
3. Turn this audit's commands into reproducible scripts/CI jobs.

Exit criterion: one command reports the known baseline for each version.

### Phase 1: repair March 5 identity and storage

1. Add semantic primitive identity and ABI/version to `PrimCanon`.
2. Remove name-index-based primitive behavior selection.
3. Add collision validation: if a CID already exists, verify stored kind and
   bytes match exactly rather than silently accepting `INSERT OR IGNORE`.
4. Introduce a store-format version/migration policy.
5. Rebuild the Hello World database from source/fixture declarations and make
   it an end-to-end test rather than an opaque hand-maintained binary.

Exit criterion: add and subtract have different CIDs; a word using each
executes correctly in the same database; the example database is reproducibly
generated and runnable.

### Phase 2: define a small conformance core

Port representative March 4 programs into backend-neutral test vectors:

- literals and arithmetic;
- stack operations;
- typed word calls and specialization;
- quotations/apply;
- conditionals and loops;
- arrays including aliasing/mutation cases;
- effects/state ordering;
- expected compile-time failures.

Each test should specify inputs, outputs, effects, and expected diagnostics.
Avoid tests whose only assertion is that compilation did not crash.

Exit criterion: the March 5 interpreter passes the conformance core and every
test exercises a persisted/reloaded graph.

### Phase 3: recover the language semantics

1. Reconcile the root semantic specification with implemented March 4 and
   March 5 behavior.
2. Decide the quotation/comment syntax and remove historical ambiguity.
3. Port March 4's type variables and specialization model into the semantic IR.
4. Specify allocation/aliasing/escape behavior before porting automatic FREE.
5. Treat the compile-time heap graph as a proof/optimization structure, not as
   an implementation detail of one backend.

Exit criterion: the semantic document, reference interpreter, and conformance
tests describe the same language.

### Phase 4A: VM backend decision gate

Before extending March 4, update its C tests and make selected language tests
assert results. Run under ASan/UBSan. If the corrected VM passes the shared
conformance core without pervasive redesign, retain it as the native backend;
otherwise use its assembly/kernel ideas in a new lowering.

### Phase 4B: interaction-net feasibility gate

Implement only a thin vertical slice:

1. lower pure literals, arguments, add/subtract, calls, and RETURN into a real
   port/principal-port net;
2. define canonical parsed rewrite rules, not opaque source strings;
3. reduce it to a result;
4. compare result and effect trace with the reference interpreter;
5. measure graph growth and reduction count.

Only after that slice works should guards, quotations, effects, or memory
management be moved into interaction-net rules.

Exit criterion: the same persisted semantic graph executes through both the
reference interpreter and the INet lowering with identical observable results.

## Immediate next task

Start Phase 1 with a narrow patch in March 5:

- redesign primitive canonical identity;
- add regression tests proving same-signature primitives remain distinct;
- replace name-based dispatch with an immutable primitive opcode/binding;
- add strict object collision checking;
- regenerate the Hello World fixture through a script or test helper.

This removes the largest threat to the CID-first architecture before further
language or interaction-net work compounds it.
